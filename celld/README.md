# celld + SvelteKit

A skeleton [SvelteKit](https://svelte.dev/docs/kit) app deployed on
[celld](https://celld.dev/docs) with the same code and configuration deployable
to Cloudflare Workers (via
[`@sveltejs/adapter-cloudflare`](https://svelte.dev/docs/kit/adapter-cloudflare)
with the `workers` target).

Scaffolded with:

```sh
bunx sv create --template minimal --types ts --add sveltekit-adapter="adapter:cloudflare+cfTarget:workers"
```

Linting is [oxlint](https://oxc.rs) + [Biome](https://biomejs.dev).

## Requirements

- [celld](https://celld.dev/docs) 0.6+
- `esbuild` on `PATH` (used by `celld dev` and `celld deploy`)
- [Bun](https://bun.com) for dependencies, type checking and linting

```sh
bun install
```

## Develop

Frontend dev server, with Cloudflare bindings emulated locally from
`wrangler.jsonc` (persisted under `.wrangler/`, separate from celld state):

```sh
bun dev
```

To serve the production build through celld (builds first, state in
`.celld/dev`):

```sh
bun run dev:celld
```

`celld dev` starts a local object store, deploys the application and rebuilds
on changes. It needs no Docker, cloud bucket or S3 emulator. Pass `--clean`
to `celld dev` directly for an empty state.

## Build

```sh
bun run build
```

This runs `vite build`, producing `.svelte-kit/cloudflare/` with `_worker.js`
plus static assets, then assembles `build/` from that output for celld.

Two celld constraints shape this step (both handled by the `build` script, so
no manual work is needed):

- celld refuses a `.assetsignore` file, which the adapter always emits, so the
  script strips it (`--exclude=.assetsignore`).
- celld refuses to publish the Worker source itself as an asset, so `_worker.js`
  (and the Pages-only `_routes.json`) are excluded from `build/`.
  `wrangler.jsonc` therefore keeps `main` at
  `.svelte-kit/cloudflare/_worker.js` and serves `assets` from `./build`.

`worker-configuration.d.ts` is generated by `wrangler types`
(`bun run gen`, best run under Node rather than Bun); the repo carries a
minimal placeholder so `bun run check` and `bun run lint` pass on a fresh
clone. Running `gen` overwrites it with the full binding types.

## Deploy

Copy the example environment file and fill in the values:

```sh
cp .env.example .env
$EDITOR .env
```

`bun run deploy` builds and then loads `.env` before invoking
`celld deploy`:

```sh
bun run deploy
```

`.env` is git-ignored; commit only `.env.example`.

`wrangler.jsonc` points `main` at `.svelte-kit/cloudflare/_worker.js` and
serves `assets` from `./build` (assembled by `bun run build`, see above).
`workers_dev` and `preview_urls` are intentionally omitted: celld rejects
unknown top-level Wrangler keys.

Start a node against the same bucket (env vars are read automatically):

```sh
celld --listen 127.0.0.1:8080
```

A running node adopts each new deployment without a restart. See the
[celld docs](https://celld.dev/docs) for R2, GCS, Azure and fleet settings.

## Persistence

The home page is a guestbook backed by a celld KV namespace. Each note is one
KV entry (`note:<timestamp>:<random>` holding JSON), listed with a prefix
scan; signing and deleting notes are SvelteKit
[remote functions](https://svelte.dev/docs/kit/remote-functions) calling `put`
and `delete`. It exercises the whole KV surface: `put`, `get`, `list`,
`delete`.

`src/routes/guestbook.remote.ts` holds a `getNotes` query and `addNote` /
`removeNote` commands; `+page.svelte` awaits the query inside a
`<svelte:boundary>` and invokes the commands from event handlers. Mutations
use single-flight refresh (`void getNotes().refresh()` in the handler), so the
list updates in the same round trip. Remote functions are experimental and
enabled in `vite.config.ts` (`experimental.remoteFunctions` plus
`compilerOptions.experimental.async`).

`wrangler.jsonc` declares the binding:

```jsonc
"kv_namespaces": [{ "binding": "GUESTBOOK", "id": "guestbook" }]
```

A KV `id` is just the namespace identity and can be any string — two Workers
naming one `id` share one namespace. Server code reads it from
`cloudflare:workers`; that is the documented way to reach bindings from
SvelteKit on Workers. The generated `_worker.js` passes `env` to
`server.init()` but never sets `event.platform` (the adapter only fills
`platform` for `vite dev` via its platform proxy), so `platform.env` stays
empty in the built worker. Without a binding the remote functions throw 503,
which the boundary renders as an error with a retry button.

celld KV notes worth knowing ([docs](https://celld.dev/docs/services/kv)):

- Reads are strongly consistent (they reach the owning cell), unlike
  Cloudflare's eventually-consistent KV.
- One writer per namespace: fine for a guestbook, but use a Durable Object
  for a write-hot value such as a counter.
- Keys ≤ 512 bytes, values ≤ 25 MiB, metadata ≤ 1024 bytes, minimum 60 s
  expiration. Values over 1 MiB need a fleet bucket.
- `list()` returns at most 1000 keys in byte order per page.

Both dev servers serve the guestbook with real persistence, but separate
stores: `bun dev` uses Wrangler-emulated bindings (persisted under
`.wrangler/`), while `bun run dev:celld` uses celld's store (`.celld/dev`).
Notes written in one are not visible in the other. Note that `celld dev`
also exposes `.env` entries as worker vars, while `celld deploy` does not —
`.env` holds bucket credentials for the CLI.

### Which store for what?

celld mirrors Cloudflare's storage services; a typical app combines them,
each declared as a binding in `wrangler.jsonc`:

- **KV** — small values by key: sessions, config, feature flags, caches,
  per-item records like these notes. Simple `get`/`put`/`list`/`delete`.
- **D1** — relational data with SQL: users, posts, anything you filter, sort,
  join or aggregate. One SQLite database per binding, migrated with
  `celld d1 migrations apply`. Prefer D1 over KV once you need queries.
- **R2** — blobs and files: uploads, images, exports. Streamed bodies and
  multipart uploads, stored under `r2/<bucket>/` in the fleet bucket (so R2
  needs a bucket configured). No public URLs — serve bytes through the Worker.
- **Durable Objects ("cells")** — stateful actors with their own SQLite DB,
  single-threaded JS, WebSockets and alarms: chat rooms, live documents,
  counters, realtime games, agents (one object per room/user/document). The
  strongest consistency and coordination primitive.
- **Queues / Workflows** — background jobs, retries and multi-step durable
  pipelines, plus **Cron Triggers** for schedules.

SvelteKit caveat, from the
[adapter docs](https://svelte.dev/docs/kit/adapter-cloudflare): Durable
Objects and Workflows need custom classes exported from the Worker, which the
adapter-generated `_worker.js` cannot do — so they are not currently usable
from the SvelteKit worker itself. KV, D1 and R2 bindings work as shown here.

## Local S3?

Use `celld dev` instead. Its built-in object store covers local development
without a second server. If you specifically need to exercise the S3 code path
locally, MinIO community edition passes celld's storage test (but is not
qualified for production); production buckets should be S3, R2, GCS or Azure
Blob Storage.
